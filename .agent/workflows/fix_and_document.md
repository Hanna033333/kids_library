# 🔧 /fix-and-document 재발 방지 워크플로우

이 워크플로우는 사용자가 `/fix-and-document`를 호출했을 때, 방금 이 대화에서 발생한 문제의 근본 원인을 분석하고, 코드를 즉시 수정하며, 동일한 실수가 다시 일어나지 않도록 에이전트 규칙 파일에 영구 기록하는 표준 절차입니다.

---

## 🔍 [Step 1] 근본 원인 분석 (Root Cause Analysis)

이 대화에서 발생한 문제를 다음 관점으로 분석합니다.

1. **증상 vs 원인 구분**
   - 사용자가 경험한 증상(UI 깨짐, 에러 메시지, 의도치 않은 동작)이 무엇인지 명확히 정의합니다.
   - 증상의 직접적 원인(함수 버그, 잘못된 타입, 누락된 필드 등)을 코드 레벨에서 특정합니다.
   - 왜 그 원인이 발생했는지 구조적 배경(DB 스키마 제약, 폴백 로직 사이드이펙트 등)까지 추적합니다.

2. **영향 범위 확인**
   - 동일한 버그 패턴이 다른 스크립트나 파일에도 존재하는지 검색합니다.
   ```bash
   grep -rn "문제가 된 패턴" backend/ frontend/ --include="*.py" --include="*.ts"
   ```
   - 이미 잘못 삽입/저장된 데이터가 있다면 식별 방법과 정리 절차를 함께 안내합니다.

---

## 🛠️ [Step 2] 코드 수정 (Code Fix)

근본 원인을 코드에서 직접 수정합니다.

1. **수정 대상 파일 특정**: 버그가 있는 함수/라인을 정확히 찾아 수정합니다.
2. **영향 범위 일괄 수정**: 동일 패턴이 여러 파일에 있다면 모두 수정합니다.
3. **수정 후 간단 검증**: 가능하다면 소규모 테스트 삽입 → 확인 → 삭제로 수정이 유효한지 즉시 확인합니다.

---

## 📝 [Step 3] 재발 방지 규칙 문서화

수정한 내용을 에이전트가 앞으로 동일한 실수를 하지 않도록 규칙 파일에 영구 기록합니다.

### 대상 파일 결정
| 문제 영역 | 기록 파일 |
|---|---|
| 백엔드/프론트엔드 코드, DB 스키마, API | `.agent/rules/development.md` |
| UI 컴포넌트, 레이아웃, 디자인 시스템 | `.agent/rules/design.md` |
| 배포, 브랜치, 환경변수 | `.agent/rules/deployment.md` |
| 마케팅, 콘텐츠, 스레드 | `.agent/rules/marketing.md` |

### 규칙 작성 원칙
규칙은 반드시 다음 세 가지를 포함해야 합니다.

```
- **[제목] (재발 방지)**:
  - [무엇이 문제였는지]: 구체적 에러 메시지나 증상을 명시합니다.
  - [왜 발생했는지]: DB 제약, 타입 불일치 등 구조적 원인을 설명합니다.
  - [어떻게 수정해야 하는지]: 올바른 코드 패턴 또는 규칙을 명시합니다.
  - [잘못된 케이스 식별 방법]: 이미 발생한 케이스를 찾는 쿼리나 조건을 기록합니다. (해당 시)
```

### 규칙 등록 위치
- 기존 관련 번호 항목 하단에 하위 bullet로 추가합니다.
- 완전히 새로운 주제라면 기존 최고 번호 다음에 새 번호로 추가합니다.
- **반드시 한글로 작성**합니다.

---

## ✅ [Step 4] 완료 보고

다음 내용을 사용자에게 요약 보고합니다.

1. **문제 요약**: 증상과 근본 원인 1~2줄
2. **코드 수정 내용**: 수정한 파일 경로와 변경 사항
3. **규칙 추가 위치**: 어떤 `.md` 파일 몇 번 항목에 추가됐는지
4. **재발 방지 포인트**: 앞으로 이 실수를 막는 핵심 체크 포인트
