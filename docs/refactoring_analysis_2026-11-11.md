# 책자리 전체 리팩토링 분석

분석일: 2026-11-11. 현재 로컬 작업 트리 기준이며 기존 미커밋 변경 9개를 포함한다. 애플리케이션 코드는 수정하지 않았다.

## 판단

전면 재작성보다 **오류 경계 보강 → 조회 계약 통일 → 공통 상태 추출 → 화면 분리** 순서가 적합하다. Next.js / FastAPI / Supabase / React Query 구성은 유지한다. 이미 존재하는 `curation-filter`, `curation-link`, `apiFetch`, `visibleBooks`를 확장하는 편이 새로운 추상화 계층을 대량 도입하는 것보다 효과적이다.

현재 문제의 중심은 파일 길이 자체보다 동일한 정책이 서버 렌더링, 브라우저, 백엔드에서 서로 다르게 구현되는 점이다. 화면 분리만 먼저 하면 이 차이가 작은 파일들로 옮겨갈 뿐이다.

## 분석 범위와 검증

- 프론트엔드 TS/TSX 106개, 16,248줄. 백엔드 Python 185개, 26,055줄. 의존성·빌드 산출물 제외, 스크립트·스토리 포함.
- 주요 검토: 홈/목록/상세/내 책장/마이페이지, 인증·도서관 Context, 데이터 접근 모듈, 검색·도서·리뷰·인증 API, Threads 발행, 설정·스키마·테스트.
- `npm run lint`: 통과.
- `tsc --noEmit --incremental false`: 통과.
- 주간 일정 JSON 두 사본: 현재 내용 동일.
- 실제 앱 라우터의 최초 매칭 확인: `/api/books/my-reviews`가 `/api/books/{book_id}`에 매칭됨.
- 외부 DB 호출 전 종료되는 로컬 TestClient 요청으로 재현: `GET /api/books/my-reviews` → 422(`path.book_id`), 대출 조회 72개 ID → 400, 도서 일괄 조회 51개 ID → 400. lifespan은 실행하지 않아 스케줄러·리스너를 구동하지 않았다.
- 운영 DB 데이터, 실제 RLS, 모바일 화면, API 응답 시간·번들 크기는 검증하지 않았다. 전체 빌드와 외부 연동 통합 테스트도 실행하지 않았다.
- 백엔드 테스트에는 실제 DB 검색을 수행하는 경로와 환경변수 변경이 있어 이번 읽기 중심 분석에서는 전체 실행하지 않았다.

## 1. 먼저 해결할 기능 오류와 회귀 위험

### P1 — 내 리뷰 조회 경로가 상세 경로에 가려짐

근거: `backend/main.py:94`, `backend/main.py:99`, `backend/api/books.py:159`, `backend/api/reviews.py:406`.

도서 라우터를 먼저 등록하고 그 안에 `/{book_id}`가 있어, 뒤에 등록된 `/api/books/my-reviews`에 도달하지 못한다. `book_id: int` 타입 선언은 문자열 경로 매칭 자체를 막지 못한다. 프론트엔드 `getMyRatedBooks()`가 이 경로를 호출한다.

개선: 정적 경로를 동적 경로보다 먼저 등록하거나, 정수 경로 변환기를 사용하거나, 사용자 리뷰 목록을 `/api/me/reviews`로 이동한다. 기존 URL을 보존하는 최소 수정부터 권장한다. 이 경로가 인증 의존성을 통과해 올바른 핸들러에 도달하는 회귀 검증이 필요하다.

### P1 — 목록 누적 조회와 내 책장이 서버의 50권 제한과 충돌

근거: `frontend/components/BookList.tsx:287`, `frontend/app/my-library/page.tsx:65`, `backend/api/books.py:74`, `backend/api/books.py:135`.

목록은 누적된 `displayBooks` 전체 ID를 대출 조회에 보낸다. 일반 목록이 24권씩 3페이지 누적되면 72권이 되어 서버 제한에 걸린다. 저장 도서가 51권 이상인 내 책장도 `by-ids`와 대출 조회에 전체 ID를 보내 실패한다.

개선: 공통 배치 함수에서 ID 중복 제거, 최대 50개 분할, 동시 요청 수 제한, 결과 병합을 처리한다. 목록은 새로 추가된 도서만 조회하고 도서관+도서 ID 단위로 캐시를 재사용한다. 큰 저장 목록은 서버 페이지네이션도 검토한다. 경계값 0/1/50/51/72권을 검증한다.

### P1 — 청구기호 정렬이 전체 결과를 메모리에 읽고 나서 페이지를 자름

근거: `backend/services/search.py:110`.

청구기호 정렬은 페이지 범위 없이 도서 검색 결과를 가져오고 도서관 정보를 추가 조회한 뒤 Python에서 정렬·슬라이스한다. 페이지마다 전체 조회와 정렬을 반복하며, Supabase 응답 최대 행 수에 걸리면 일부 도서만으로 전체 건수와 정렬을 계산할 수 있다. 실제 제한값과 잘리는 도서 수는 미확인이다.

개선: DB 함수/RPC 또는 뷰에서 선택 도서관 조인, 미소장 후순위 정렬, 페이지네이션, 전체 건수를 처리한다. 기존 결과와 비교하면서 이전한다. 같은 청구기호·제목의 안정적인 순서를 위해 ID를 마지막 정렬 기준으로 둔다.

### P2 — 초기 목록의 페이지 정보를 임의로 축소

근거: `frontend/hooks/useBooks.ts:71`, `frontend/components/BooksPageClient.tsx:317`.

서버가 계산한 전체 건수와 페이지 정보를 버리고 `Book[]`만 전달한다. 훅은 `total = initialBooks.length`, `total_pages = 1`로 초기화하므로 실제 API 재조회가 끝나기 전까지 다음 페이지가 없다고 판단한다. 초기 데이터가 fresh로 취급되는 30초 동안 발생할 수 있으며, 초기 데이터 전달 조건에는 정렬 일치 여부도 빠져 있다. 쿼리 키에는 요청 크기 `limit`도 없다.

개선: 초기 데이터를 `BooksResponse` 형태로 전달하고 실제 요청 조건이 일치할 때만 사용한다. 정렬·페이지 크기를 포함한 공통 쿼리 키 생성기를 만든다.

### P2 — 계정 변경과 도서관 변경에 취약한 수동 상태

근거: `frontend/app/my-library/page.tsx:36`, `frontend/app/my-library/page.tsx:55`, `frontend/app/my-library/page.tsx:88`.

저장 목록 요청에 취소/세대 검사가 없어 빠르게 도서관을 바꿀 때 이전 응답이 마지막 화면을 덮을 수 있다. `ratedLoaded`는 사용자 ID별 상태가 아니며 로그아웃·계정 변경 때 초기화되지 않는다. 같은 컴포넌트 인스턴스가 유지되면 이전 계정의 조회 결과가 남을 가능성이 있다.

개선: `['wishlist', userId]`, `['my-reviews', userId]`, `['loan-status', library, bookId]`로 서버 상태를 관리하고 계정 변경 시 개인 캐시를 정리한다. 비로그인 렌더링 조건만으로 데이터 초기화를 대신하지 않는다.

## 2. 구조 리팩토링의 핵심

### 조회 정책을 계약으로 통일

근거: `frontend/lib/books-api-server.ts`, `frontend/lib/home-api.ts`, `frontend/lib/caldecott-api.ts`, `backend/services/search.py`.

초기 서버 목록과 클라이언트 목록이 별도 조회 구현이다. 큐레이션 매핑, 첫 태그 매칭, 숨김·이미지 조건, 연령 별칭, 정렬을 여러 곳에서 관리한다. 서버 초기 조회는 `callno` 요청을 제목순으로 처리하지만 백엔드는 선택 도서관의 청구기호순으로 처리한다. 따라서 같은 URL의 초기 결과와 재조회 결과가 달라질 여지가 있다.

단계적 개선:

1. `BookSearchInput`, `BookSummary`, `BookDetail`, `BooksPage` 계약을 먼저 정의한다.
2. 기본 정렬, 특수 태그, 연령 매핑, 도서관 ID를 공유 데이터로 정리한다.
3. 같은 입력의 서버/브라우저 조회 결과를 대조하는 계약 테스트를 추가한다.
4. 핵심 필터·정렬을 DB 함수 또는 백엔드 서비스 한 곳으로 수렴한다. 홈 ISR을 유지하며 API 의존성 증가와 응답 시간은 측정 후 결정한다.

모든 조회를 무조건 FastAPI로 옮기는 방식은 권장하지 않는다. 홈의 정적 렌더링 및 외부 API 장애 영향까지 함께 고려해야 한다.

### 찜하기·대출·로그인 복귀 동작을 공통 훅으로 추출

목록, 상세, 내 책장, 마이페이지가 찜 목록과 로딩 상태를 각각 보유한다. 로그인 후 `pendingAction`, 찜 상태 갱신, 오류 복구도 중복된다.

권장 경계:

- `useWishlist(userId)`: 목록 조회, 저장/해제, 낙관적 갱신과 복구, 캐시 무효화.
- `useLoanStatuses(bookIds, library)`: 50권 분할, 중복 제거, TTL, 오류 상태.
- 로그인 복귀 처리: 세션에 저장된 작업을 한 곳에서 소비하고 완료 시점을 명확히 한다.
- UI는 클릭 이벤트와 표시를 담당하고 저장소·네트워크 처리는 훅이 담당한다.

현재 비로그인 찜 클릭은 로그인 유도 경로이며, 계획서의 로컬 저장 찜 정책과 차이가 있다. 이 부분은 구조 변경과 기능 정책 변경을 분리해서 다룬다.

### 큰 화면은 책임을 기준으로 분리

| 대상 | 현재 규모 | 분리 경계 |
| --- | ---: | --- |
| `BookDetailClient.tsx` | 909줄 | 표지/기본 정보, 대출 패널, 추천 섹션, 찜 훅, 미리보기 |
| `BookReviewSection.tsx` | 844줄·상태 23개 | 요약, 목록, 작성/수정 공통 폼, 리뷰 mutation |
| `MyPageClient.tsx` | 643줄 | 프로필, 닉네임 편집, 탈퇴 폼, 책장 미리보기 |
| `BookList.tsx` | 568줄 | 목록 조회, 추천 폴백, 찜, 대출 조회, 스크롤 감지 |
| `backend/api/threads.py` | 1,197줄 | HTTP 라우터, 승인 화면 템플릿, 생성 서비스, 발행 서비스, 스케줄러, Telegram 리스너 |

줄 수 목표만으로 나누지 않는다. 폼 상태는 관련 필드를 한 객체 또는 reducer로 묶고, 서버 상태는 React Query에 둔다. 화면을 쪼개기 전에 중복 동작을 추출해야 props 전달 복잡도가 줄어든다.

### 자동 발행을 API 서버 생명주기에서 분리

근거: `backend/main.py:21`, `backend/api/threads.py:560`, `backend/api/threads.py:909`.

일반 도서 API 기동에도 Threads 관리자 토큰이 필요하며 각 서버 프로세스가 스케줄러와 리스너를 실행한다. 최종 발행에는 DB 원자적 선점이 있어 이미 중복 방어가 존재하지만, 생성·폴링·실행 상태까지 프로세스 수에 독립적인 것은 아니다. 즉시 발행과 예약 발행에도 유사한 본문이 반복된다.

개선: 우선 단일 발행 서비스로 합치고 자동 작업 활성화 설정을 분리한다. 이후 전용 worker 실행 명령을 제공한다. 발행 중 선점 표시와 실제 완료를 모두 `published_at`에 표현하는 대신 `status`, `claimed_at`, `published_at`, `external_post_id`를 분리하고 중단된 작업의 복구 정책을 둔다. 즉시 큐/Redis 인프라를 도입할 필요는 없다.

### 주간 큐레이션·도서관·설정의 기준을 하나로 관리

- 일정 JSON은 현재 동일하지만 두 파일을 수동 유지한다. 원본 하나에서 배포 사본을 생성하고 차이를 검사한다.
- `app/page.tsx`는 일정 공백 시 과거 일정을 선택하고 `core/taxonomy.py:167`은 예외를 발생시킨다. 동일한 공백 정책과 고정 날짜 테스트가 필요하다.
- `home-api.ts`의 로컬 시간 기반 주차/일수 계산과 다른 모듈의 UTC/KST 계산을 구분하고 한 시간 유틸리티에서 관리한다.
- 도서관 이름 목록은 `LibraryContext`와 `loan_status.py`에 중복된다. ID·이름·외부 코드를 하나의 목록에서 생성한다.
- 대출 TTL은 코드상 3분, 일부 문서는 5분이다. 실제 요구 시간을 정한 뒤 설정·문서를 맞춘다.
- `core/config.py`는 직접 파싱과 dotenv를 함께 사용하고 `override=True`로 읽는다. 환경변수 우선순위와 타입 검증을 명시한 Settings 객체로 정리한다.

### 타입과 비동기 경계를 바로잡기

- `home-api`는 일부 컬럼만 조회하고 `Book[]`로 반환한다. 공통 `Book`의 필수 `isbn`, `description`, `vol` 등과 실제 응답이 맞지 않는다. `as any`보다 용도별 DTO와 DB 생성 타입으로 해결한다.
- `backend/schemas/book.py`의 기본 정렬과 필드는 현재 검색 계약을 따라가지 못하며 도서 라우터에서 응답 모델로 사용되지 않는다. 실제 응답 모델을 연결하고 OpenAPI로 TS 타입을 생성하는 방향을 권장한다.
- 여러 `async def` 라우터와 인증 의존성 안에서 동기 Supabase `.execute()` / `get_user()`를 호출한다. 이벤트 루프를 막을 수 있으므로 동기 라우터·스레드풀 또는 비동기 클라이언트 중 일관된 경계를 선택한다.
- QA 모의 사용자 처리가 AuthContext, DB 함수, 화면, 백엔드에 퍼져 있다. 프론트엔드는 localStorage 값만으로 QA 모드가 된다. 실제 서버 인증 우회로 단정할 수는 없지만, 운영 UI에서 모의 상태가 켜지지 않도록 빌드/환경 플래그와 테스트용 Provider로 격리한다.

## 3. 테스트·운영 코드 정비

프론트엔드 Vitest 설정은 Storybook 브라우저 테스트 중심이고 `test` npm 스크립트가 없다. 스토리만으로는 페이지네이션·계정 변경·날짜 분기·배치 제한을 보호하기 어렵다. 별도 순수 로직 테스트 프로젝트와 핵심 화면 통합 테스트를 추가한다.

백엔드 `test_api.py`에는 테스트 함수 9개가 있다. 검색 테스트는 실제 DB에 의존하고 환경변수를 직접 변경한 뒤 복원하지 않는다. Threads 토큰은 import 시 고정되는데 테스트에서는 import 후 환경변수를 바꿔 테스트 의도가 불명확하다. Settings와 DB client를 주입 가능하게 하고 fixture로 환경을 복원한다.

우선 보호할 시나리오:

1. 내 리뷰 정적 경로와 도서 상세 동적 경로가 각각 올바른 핸들러에 도달한다.
2. 목록 3페이지 및 내 책장 51권 이상에서도 책과 대출 상태가 누락되지 않는다.
3. 로그인/로그아웃/계정 변경/빠른 도서관 변경 후 이전 데이터가 나타나지 않는다.
4. 초기 서버 목록과 재조회 결과의 필터·정렬·전체 건수가 일치한다.
5. KST 자정, 주 경계, 연도 경계, 일정 공백에서 홈과 발행 큐레이션이 일치한다.
6. 승인 중복 요청과 발행 중 프로세스 중단 후 재시도에서 중복 발행을 막고 복구할 수 있다.

185개 백엔드 Python 파일에는 운영 API 외에 다수의 데이터 정제·크롤링 스크립트가 포함된다. 사용 여부 확인 없이 삭제하지 말고 `운영 정기 작업 / 반복 사용 CLI / 과거 마이그레이션`으로 분류한다. 공통 설정·DB 연결·dry-run·실행 로그를 먼저 통일하고 과거 작업은 archive로 옮긴다.

로컬 앱 import 과정에서 Python 3.9 및 기존 Gemini SDK에 대한 지원 종료 경고가 출력됐다. 버전 업그레이드는 별도 호환성 작업으로 계획하고 구조 변경과 같은 변경 묶음에 섞지 않는다. 이번 분석은 최신 권장 버전이나 보안 취약점을 조사한 결과가 아니다.

## 4. 권장 실행 순서

| 순서 | 변경 묶음 | 완료 기준 |
| --- | --- | --- |
| 1 | 라우팅 충돌, 50권 분할, 초기 페이지 메타데이터 | 재현한 오류와 경계값 검증 통과 |
| 2 | 조회 DTO·쿼리 키, 찜·대출 공통 훅 | 화면 간 상태 일치, 계정/도서관 변경 검증 |
| 3 | DB 청구기호 정렬, 조회 정책 통일 | 서버/클라이언트 결과 일치, 대량 결과 누락 방지 |
| 4 | 일정·도서관·설정 단일화 | 날짜 고정 테스트와 생성 파일 차이 검사 통과 |
| 5 | 상세·리뷰·목록 화면 분리 | 기존 UI·SEO·이벤트·행동 유지 |
| 6 | Threads 서비스/worker 분리, 스크립트 정비 | API 독립 기동, 발행 재시도·복구 검증 |

각 묶음은 개별 변경으로 검토·회귀 확인한다. 기존 미커밋 작업의 범위를 보존하며 진행하고, DB 구조 변경과 순수 UI 분리를 같은 단계에 섞지 않는다. 첫 작업은 **내 리뷰 라우팅과 배치 제한 수정**이 가장 작고 효과가 명확하다.

## 5. 1단계 반영 및 검증

사용자 실행 요청 후 현재 작업 트리를 다시 확인했다. 라우터 순서 조정, API의 최대 50권·동시 3개 분할/병합, 내 책장의 50권 잘라내기 제거는 이미 반영되어 있어 기존 구현을 보존하고 회귀 검증했다.

추가 반영:

- 큐레이션/연령 서버 페이지 → 각 클라이언트 → BookList → useBooks에 `BooksResponse` 전체를 `initialPage`로 전달한다.
- 실제 `total`, `total_pages`, `page`, `limit`을 보존하고 캐시 키에 `limit`을 포함한다.
- 큐레이션은 서버 조회 정렬과 현재 정렬이 같고 검색·추가 필터가 없을 때만 초기 데이터를 사용한다. 연령 페이지도 검색/정렬/연령 일치 여부를 검사하며 `teen` 별칭을 정규화한다.
- 연령 서버 페이지에서 SEO용 추천 병합 목록과 실제 페이지 데이터를 구분했다. 추천 도서는 기존 BookList 병합 경로에서 처리해 다음 페이지와의 중복을 방지한다.
- `npm run test:unit`으로 외부 서비스 없이 요청 분할·병합 및 React Query 페이지네이션을 검증할 수 있다. 백엔드 라우팅 검증은 `PYTHONPATH=backend ./backend/venv/bin/python -W ignore -m unittest discover -s backend/tests -p test_routing.py`로 실행한다.

검증 결과: 프론트엔드 13개, 백엔드 2개 테스트 통과. 린트·TypeScript 검사 통과. 프로덕션 빌드 종료 코드 0. 다만 빌드 중 Supabase DNS 조회 실패(`ENOTFOUND`)가 있어 실제 DB 기반 정적 페이지 내용은 미검증이다. 배포는 수행하지 않았다.
